# Harnessy Android companion

English | [中文](<README.zh.md>)

## Summary

The native Kotlin/Jetpack Compose application provides pairing, existing-session chat, explicit opening of eligible cold chats, approved text history/progress, and queued follow-ups to a running PC. Material 3 screens use lifecycle-aware ViewModel/StateFlow state, Hilt ownership, Compose navigation and DataStore appearance preferences. The Java protocol/storage core remains behind Kotlin interoperability; separate PC consent enables four chat-management actions. Agents, privileged tools, provider credentials and session storage stay PC-owned. Build, JVM, device, pairing and background-delivery evidence are separate; source alone establishes none of them.

<a id="application-assembly"></a>
## Application assembly

[NativeActivity](<app/src/main/java/io/harnessy/companion/nativeapp/NativeActivity.kt>) hosts the [Material 3 navigation/screens](<app/src/main/java/io/harnessy/companion/nativeapp/NativeCompanionApp.kt>) declared by the [manifest](<app/src/main/AndroidManifest.xml>). An Activity-scoped [ViewModel](<app/src/main/java/io/harnessy/companion/nativeapp/CompanionViewModel.kt>) exposes immutable StateFlow snapshots through a main-thread [repository adapter](<app/src/main/java/io/harnessy/companion/nativeapp/CompanionRepository.kt>).

The phone filters already-loaded conversations in a searchable drawer; wide layouts can show navigation beside chat. The native sidebar header keeps the Harnessy brand separate from the debug launcher label, with circular search and Close controls above a divider; compact rails show the brand mark without the wordmark. Flat row highlights distinguish selection, press, pointer hover and keyboard focus. Navigation can be hidden and reopened on phone and wide layouts.

The [Work landing](<app/src/main/java/io/harnessy/companion/nativeapp/NativeWorkLanding.kt>) offers flat, vertically scrollable rows of real, already-loaded PC conversations rather than new-task suggestions; delivery and error notices take priority over recent conversations. The IME-aware [adaptive composer](<app/src/main/java/io/harnessy/companion/nativeapp/NativeComposer.kt>) uses a borderless theme-aware card and a session-local model selector, omits redundant ready/no-selection helper copy, requires a selected conversation before editing, and keeps closed conversations read-only. Short keyboard windows use a compact row while retaining the draft, focus and header controls; full notices return when the keyboard closes. Forget and delivery review require explicit confirmation. EN/ZH resources and neutral light/dark themes remain native, with no WebView or remote JavaScript.

[Settings](<app/src/main/java/io/harnessy/companion/nativeapp/NativeSettingsScreen.kt>) uses compact, accessible theme choices and displays the PC-reported chat-management permission with desktop setup guidance when permission is denied. Opening navigation clears draft focus and dismisses its keyboard; sidebar search reserves keyboard space. Navigation controls and sessions share one scrolling list below the fixed header and search field. With the keyboard dismissed, system Back closes the phone drawer without leaving chat.

The [transcript](<app/src/main/java/io/harnessy/companion/nativeapp/NativeTranscriptModel.kt>) folds consecutive tool-name rows into local [Activity disclosures](<app/src/main/java/io/harnessy/companion/nativeapp/NativeToolActivity.kt>), separate from assistant prose. Notices remain visible outside disclosures, including turn failures; isolated tool names have no empty expansion control. Exact known tool names select existing Desktop glyph families; unknown names use the generic glyph. Expanded names keep their original order and literal text inside a bounded scrolling body; toggling brings the group into view. View state survives appends to the same group, but resets on conversation changes, Activity recreation or removal of the group's first retained row; it never invokes a PC tool. These are adjacent names, not reconstructed Desktop turns or call/result pairs; tool inputs, result bodies, per-tool state and timing are not supplied. Tool activity currently arrives through live progress, not historical text pages.

[CompanionController](<app/src/main/java/io/harnessy/companion/CompanionController.java>) owns one foreground epoch and one current attempt. `onStart` loads and revalidates stored metadata and connects automatically; `onStop` invalidates immediately, cancels controller deadlines/reconnects/subscriptions, closes transport, and discards invitations. Retired callbacks cannot publish or send. A new attempt waits for the old transport’s `quiescence()`. Configuration recreation retains the controller’s bounded RAM draft and selection but not network activity. Drafts are keyed by PC and chat; process recreation restores no task text or draft. There is no background service, offline queue, push notification, or cloud-account promise.

[HarnessyApplication](<app/src/main/java/io/harnessy/companion/HarnessyApplication.kt>) and the [Hilt modules](<app/src/main/java/io/harnessy/companion/nativeapp/CompanionModules.kt>) share one bounded serialized [AndroidCompanionPlatform](<app/src/main/java/io/harnessy/companion/AndroidCompanionPlatform.java>) owner. Preferences/keystore work and signing run off the UI thread; transport retirement is awaited across Activity instances. Controllers are ViewModel-scoped, not application singletons. [NativePreferences](<app/src/main/java/io/harnessy/companion/nativeapp/NativePreferences.kt>) stores only ordinary appearance settings in DataStore; key aliases, pairing metadata, repair markers and delivery fences retain their existing storage semantics. No Room database or phone-owned session cache is introduced.

Every reconnect constructs a fresh [PhoneTransport](<app/src/main/java/io/harnessy/companion/transport/PhoneTransport.java>) with the saved phone alias, pinned canonical HTTPS origin/PC key, and authenticated grant generation. Protocol nonce, ephemeral ECDH key, channel ID, and counters are fresh. Transport itself never reconnects. The controller retries at a configured minimum interval for as long as it remains foreground; it has no finite total attempt limit. Missing keys and invalid storage stop automatic attempts and require explicit repair. Online means mutual encrypted key confirmation, not inbox admission or completed work.

<a id="workspace-navigation"></a>
## Workspace navigation

[Native session navigation](<app/src/main/java/io/harnessy/companion/nativeapp/NativeSessionNavigation.kt>) groups loaded conversations by PC-declared Workspace identity and order.

Folder open/closed choices persist in phone DataStore by PC and Workspace identity across navigation and app restarts; new folders start closed. Search temporarily reveals matching folders without overwriting those choices. These phone-local choices do not mirror or modify the Desktop sidebar. Unassigned conversations have no folder header.

The navigation view mirrors PC-global pins, ordered first within each group, followed by recency. Separate PC-approved actions can change pins. Each group initially shows up to five conversations, or all pinned conversations if there are more than five; Show more reveals the remaining loaded rows. Title/Workspace-name search and the Open filter are local to loaded rows, not PC-wide search. Folder and pin glyphs reuse Desktop geometry.

Relative age uses the PC's later-of-creation-and-last-durable-human-prompt time, not assistant completion. Missing metadata never creates an inferred folder, pin or age. Progress status updates preserve previously received navigation metadata. Navigation exposes no file paths and no empty-Workspace inventory. **New chat** uses a separate permission-gated picker of real registered Workspaces, including registered empty groups, and creates an empty Session with the PC default preset, without human text or model/provider controls. Row menus offer typed, RAM-only Rename input, Archive and Pin/unpin after PC opt-in; permanent Delete is deferred with no wire command or UI. Archive refuses busy chats, retains history and drops their pin; it offers no Stop shortcut. Renaming and text submission require an already-open chat. New chat and archiving any chat cannot discard a nonempty draft. Management gestures bind to the foreground generation, PC and target; a delayed Create acknowledgement cannot replace a newer selection or draft. See [permission and update order](<../../docs/upgrade-guide/v0.1.15/companion-chat-management/guide.md>).

Ordinary listings request `view: 'navigation'`; heartbeat listings remain legacy requests. **Update the PC before using this phone API.** An older PC's exact-field parser rejects the view request and closes the channel; there is no permissive compatibility fallback. Old phones that omit the view continue to receive legacy rows from an updated PC. Follow the [upgrade guide](<../../docs/upgrade-guide/v0.1.15/companion-navigation/guide.md>); source changes do not update a running PC or establish device acceptance.

<a id="model-selection"></a>
## Model selection

The Gradle property `companion.pcModelSelection` defaults to `true`. When enabled, the [model selector](<app/src/main/java/io/harnessy/companion/nativeapp/NativeModelSelector.kt>) fetches one bounded PC catalog page when opened; it never invents models or exports provider routes. Deploy matching PC support before use; reading or selecting still requires separate per-phone model consent. Selection binds the rendered foreground, PC, chat, revision and opaque choice, accepts only an idle live chat, and preserves the draft. Its minimal `selectSessionModel` fence precedes any possible transport write; only a correlated outcome and confirmed fence clear update the displayed selection. Unknown outcomes block further changes/sends until explicit review; nothing replays automatically. See [update order and downgrade restrictions](<../../docs/upgrade-guide/v0.1.17/companion-model-and-tool-consent/guide.md>).

For Android-only UI work with a PC that lacks model support, set `-Pcompanion.pcModelSelection=false`; the model control explains the missing support without querying or selecting models. Only `true` and `false` are accepted. This opt-out does not grant PC permission or reset phone storage.

<a id="session-activation"></a>
## Session activation

An eligible existing cold ordinary chat can be opened explicitly on the running PC with [Open chat](<app/src/main/java/io/harnessy/companion/nativeapp/NativeSessionActivation.kt>); no Desktop tab is required. Session listing and history reads never activate a PC Agent. Opening requires the separate per-phone PC permission exposed as **Enable opening chats** in **Paired phones**; pairing, chat-management, model-selection and tool-detail grants do not imply it. The operation resumes an existing chat through normal PC Agent initialization and a targeted Session flush; initialization may migrate or repair history or run SessionStart plugins, even if it fails. It sends no text or new task and leaves other chats and global model defaults unchanged. A missing reply after admission leaves an uncertainty fence; the phone does not retry automatically. See the [session activation upgrade guide](<../../docs/upgrade-guide/v0.1.17/companion-session-activation/guide.md>).

<a id="pairing-and-storage"></a>
## Pairing and storage

Opening a link imports but never enrolls automatically. The no-history/no-display [InvitationActivity](<app/src/main/java/io/harnessy/companion/nativeapp/InvitationActivity.kt>) accepts only the `harnessy` scheme and `pair` host, clears incoming Intent data/extras/ClipData, and hands off bounded text through a single-use RAM inbox. The retained main task receives a clean Intent without the invitation; restoration is not a fresh delivery. Pairing is capture-protected, Recents screenshots are disabled on API 33+, and secure-window protection covers older devices. No URL is navigated. [Invitation.parse](<app/src/main/java/io/harnessy/companion/protocol/Invitation.java>) requires exact canonical `harnessy://pair#` text, version/field/key/origin/PC-ID validation, and unexpired invitation data. Cancel, expiry, background, and authenticated success drop invitation/link/secret references; Java/provider buffer erasure remains best effort.

**Settings → PC connection → Link a PC** opens the pairing form without forgetting an existing PC. Explicit Pair creates a new per-enrollment alias through [PhoneIdentity.createForPairing](<app/src/main/java/io/harnessy/companion/identity/PhoneIdentity.java>). The pairing view displays the full 64-character lowercase SHA-256 fingerprint of the phone’s public SPKI DER for comparison with the PC dialog. The signer uses `signTranscript(alias, bytes)`; it never exports the private key. An existing pairing must be explicitly forgotten before that same PC is enrolled again. Missing or invalid paired keys are never silently replaced.

Only authenticated `onConfirmed` grant ID/generation, pinned PC key/origin/derived PC ID, and the phone alias enter [PairingStore](<app/src/main/java/io/harnessy/companion/pairing/PairingStore.java>). The displayed PC name is a generic localized local label because the wire has no name. Stored metadata is revalidated against [Protocol](<app/src/main/java/io/harnessy/companion/protocol/Protocol.java>) before use. The UI uses the first stored PC. Saving an explicitly enrolled PC places it first, so foreground and process restoration retain that selection without removing other pairings or key aliases. The store retains up to 32 records; the UI does not offer a saved-PC chooser.

[OperationStore](<app/src/main/java/io/harnessy/companion/pairing/OperationStore.java>) retains at most 32 minimal delivery fences and 32 public PC-ID/alias repair markers. The existing single preferences document reads valid v1/v2 without rewriting them; the next legitimate write emits v3 while preserving fences and repair markers, without changing pairing keys. V3 fences are keyed by PC ID and Session ID and contain only `{kind, pcId, sessionId, operationId}`: no titles, Workspace IDs, text or retry payloads. Fence removal compares the exact expected fence before clearing it. A repair marker precedes enrollment persistence or local forget. A failed SharedPreferences `commit()` may change memory without confirmed disk durability: the controller stays fenced and retains the alias, rather than claiming rollback or deleting a potentially referenced key. A repair marker can identify an alias even when settled pairing metadata is absent. Corrupt/version-unknown documents are not reset automatically. Confirmed storage settlements survive foreground retirement and reconcile with fresh metadata before further storage mutations; clearing delivery uncertainty does not clear an independent pairing-repair blocker.

Forget is local, not PC revocation. The Activity warns before it fences/stops the owner, commits metadata removal, deletes only the exact phone alias after that commit succeeds, then clears the repair marker. A failed metadata commit retains the alias and fence. Preference/keystore operations are not a cross-store atomic transaction. Uncertainty fences survive forget; revocation or forgetting does not erase work already admitted on the PC. Check the original session before resetting corrupt application data.

<a id="reads-and-delivery"></a>
## Reads and delivery

The [application codec](<app/src/main/java/io/harnessy/companion/protocol/ApplicationCodec.java>) consumes validated immutable DTOs for the closed [read, text and management operation set](<../../packages/util/companion-protocol/README.md#application-management-compatibility>), including [explicit session activation](<../../packages/util/companion-protocol/README.md#application-session-activation>). Every request uses a fresh correlation ID. Pending reads and deadlines are bounded independently of mutations. Reconnect recreates only reads/subscriptions, retaining same-session text while refreshing authority. Active sessions establish an acknowledged live subscription before reading history; renewal cancels the previous subscription before repeating that sequence. Closed sessions read approved history without subscribing; a resumed closed chat must obtain a fresh watch acknowledgement before live reads. A management acknowledgement never supplies watch authority. Closing progress retires only its watch, leaving independent history reads intact. Baselines merge with the bounded live window; an unknown watch/cancel outcome closes the attempt to prevent accumulating remote subscriptions. Correlated recovery can clear only a read-failure notice, never a storage, repair, send or delivery warning.

Separate native load-more controls round-trip opaque listing/history cursors through their issuing operation. Progress cursors never become history cursors. Progress requires the exact subscription ID, selected session, and current epoch/attempt. Row IDs and sequences are deduplicated within the bounded, sequence-ordered retained text window. The [native CommonMark projection](<app/src/main/java/io/harnessy/companion/nativeapp/markdown/NativeMarkdownFormatter.kt>) runs off the UI thread, bounds AST depth/nodes and complete output, and falls back to the original approved text for unsupported content. Quotes, rules and reference definitions preserve surrounding formatting. HTML stays literal; links/images become text without navigation or network loading. No scripts or raw tool arguments execute. The Kotlin adapter binds Send to the rendered foreground generation, PC, session and draft, and rejects malformed/over-budget UTF-8 edits without replacing the previous valid input. Queued/running is a busy display status but still allows queued follow-ups; closed sessions deny the composer. No unsupported approval status is inferred from error codes.

Explicit Send requires a confirmed connection, an existing non-closed selected session, and no pending mutation/uncertainty fence. The controller freezes session/text/request/submission IDs and commits a minimal v3 `submitText` fence before any possible transport write. No task text or resend payload is persisted. `ADMITTED_MAY_WRITE` is uncertain until an exact matching `submitted` result with `admission=inMemoryInbox`; that result acknowledges only a volatile PC inbox, never durability or task completion. The draft clears only after a confirmed fence-removal commit and only if it is unchanged.

Disconnect, timeout, or foreground retirement after possible admission retains `DELIVERY_UNKNOWN`; reconnect/process restart never resends. Failed pre-send fence commits prevent sending; failed fence-removal commits keep the composer blocked even if preference memory changed. The original session/submission IDs remain visible. The localized Review/discard action requires a native confirmation after the user checks the original session, commits removal of only the warning, and enables a new explicit Send without resending, cancelling, or erasing the previous task.

Management writes use the same commit-before-possible-write fencing and never replay automatically. `managed` completion follows the [PC owner's commit/flush policy](<../../packages/host/companion-host/INTEGRATION.md#actual-relay-and-endpoint-wire>); partial or unknown outcomes require explicit review of the known PC/Session/operation, not a **Task queued** notice. A failed fence commit prevents the write; compare-and-clear failure leaves the action blocked. Review removes only the exact uncertainty warning, not the PC operation.

<a id="limits-and-verification"></a>
## Limits and verification

[XML budgets](<app/src/main/res/values/limits.xml>) explicitly supply [ControllerLimits](<app/src/main/java/io/harnessy/companion/ControllerLimits.java>) and [TransportLimits](<app/src/main/java/io/harnessy/companion/transport/TransportLimits.java>): reconnect minimum 5 s, reads 10 s, mutation ACK 15 s, read-only heartbeat 20 s, watch renewal 60 s, 8 pending reads, 64-row pages, 256 sessions, and 256 rows/256 KiB retained text. Heartbeat is bounded `listSessions(limit=1)`, not a new wire verb; native ping is disabled because the current broker rejects ping/pong and counts only application frames as activity. OkHttp allocates complete incoming text before listener retention checks; these budgets do not claim a preassembly memory cap.

[Kotlin DSL build declarations](<app/build.gradle.kts>) define the Android-only Compose/Hilt/KSP stack, JDK 17 bytecode, compile/target SDK 37 and minimum SDK 26. The genuine [Windows wrapper](<gradlew.bat>) and [wrapper properties](<gradle/wrapper/gradle-wrapper.properties>) pin Gradle 9.6.0 with its publisher SHA-256. With Java/SDK locations configured, run `:app:assembleDebug`, `:app:testDebugUnitTest`, `:app:lintDebug` and `:app:assembleDebugAndroidTest` through that wrapper. The debug application ID ends in `.debug` and is separate from the signed release. Signing material stays outside source control. The manifest disables cleartext and backup/device transfer.

Verification sources: [Java core/JUnit entry](<app/src/test/java/io/harnessy/companion/NativeCoreRegressionTest.kt>), [repository lifecycle/input](<app/src/test/java/io/harnessy/companion/nativeapp/CompanionRepositoryMigrationTest.kt>), [rendered-send binding](<app/src/test/java/io/harnessy/companion/NativeSubmissionBindingTest.kt>), [Markdown projection](<app/src/test/java/io/harnessy/companion/nativeapp/markdown/NativeMarkdownFormatterTest.kt>), [model delivery safety](<app/src/test/java/io/harnessy/companion/ModelSelectionControllerTest.kt>) and [Compose device checks](<app/src/androidTest/java/io/harnessy/companion/nativeapp/NativeChatMigrationTest.kt>). Source coverage and instrumentation APK compilation are not executed device evidence.

Prefer a physical Android device for USB/wireless ADB, Android Studio/Logcat and Compose UI checks; the emulator is optional. Debug-only [Compose previews](<app/src/debug/java/io/harnessy/companion/nativeapp/NativeChatPreviews.kt>) create no sockets or storage. Actual acceptance requires keystore/storage behavior, foreground/configuration/process restoration, invitation routing and capture protection, EN/ZH/light/dark/phone/tablet/landscape/large-font/TalkBack/IME behavior, backup exclusions and encrypted PC interoperability. On API 26–32 secure-window protection also blocks screenshots/scrcpy; newer devices permit ordinary chat capture but not pairing capture. APK build/signature success does not establish device or connectivity acceptance.

<a id="known-limitations"></a>
## Known limitations

The current PC protocol does not provide account switching/auto-switch, usage/banked resets, partial assistant-text streaming, remote tool approvals, attachments or closed-app push. Management and model selection remain independently default-denied until the PC grants each; Settings explains PC-owned capabilities without inventing account, model or push state. Account changes require a separate PC-approved capability; provider credentials must never leave the PC. Background notifications need configured push infrastructure and a PC-owned producer, not a persistent phone socket. Markdown supports native typography/code, not syntax highlighting; unsupported structures retain their original text.
