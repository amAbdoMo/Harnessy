# Agent Note: Harnessy edits the unified subagent roster from one Settings page

Status: implemented

[English](2026-09-16-subagents-settings-page.md) | 中文

## 问题

统一的角色目录把「角色」确立为用户配置的单位：角色固定其后端、模型策略、沙箱访问级别、调用方式、工具范围与固定指令，而两个面向模型的工具会在每次调用时读取该文档。浏览器中却没有任何东西能写入它。

有三个界面都接近，但都不合适。委派页面拥有的是 Command Code 通道文档——命名空间不同、字段集不同，而且它的访问词汇（`read-only` / `full-access`）并不是角色所命名的沙箱阶梯。Plugins 分区会为每个设置命名空间提供一张卡片，但卡片只是标签页中的一列，无法承载带模型选择器、高级区块与按工作区覆盖编辑器的角色目录。子代理卡片上的自动路由控件已经存在，但它写入的是 `subagent-model-selection`，而角色目录是从自身分区内的 `automaticRouting` 解析授权的。

模型选择器是最尖锐的约束。`ui-model-selection` 中的 `ModelSelect` 会把选择提交给实时会话，而不是发出受控取值；一个客户端插件不得导入另一个插件的组件，而给 UI 插件增加值导出需要专门批准。因此没有任何可复用的受控模型控件可以作为基础。

## 决策

`@deepseek-ai/dsh-client-ui-settings-subagents` 贡献一个顶层 **子代理** 页面（`settings.section`，id 为 `subagents`，order 为 20），仅在浏览器产物按 `custom-harness` 构建时注册，并在新的 `settings.subagents` 语言命名空间下声明其文案。

该页面按「谁拥有真相」来划分各界面。所有可编辑取值都来自 `subagent-roster` 设置分区，经 `settingsScope` 写入，并且只持久化一次编辑真正改动的顶层字段，因此同一次设置往返周期内的两次编辑会组合，而不会互相覆盖。所有*已解析*的取值都来自 Host：`resolvedRoster(workspace)` 提供委派实际会使用的取值与逐字段覆盖来源，`storedRoster()` 提供页面所报告的已存运行上限，`automaticRouting()` 提供路由区块所解释的授权。工作区来自当前会话的 `cwd`，通过标准的 `useSessions` 座位获取，没有会话时为 `null`。

模型与推理强度选择器就构建在本包内、基于共享目录，这正是架构简报所推荐的方案，优于把控件提升到 `ui-primitives` 并重构输入区座位。有三条规则让它保持诚实。存储的取值是一条精确的 `{ provider, model, reasoningEffort? }` 路由。推理强度控件只提供 `model.reasoning.efforts` 实际公布的级别，而未公布任何级别的模型会得到一段说明文字，而不是被捏造出一个级别。更换模型会重新收窄该清单，并清除新模型未公布的推理强度，因为该推理强度属于它所替换掉的那条路由。目录不再公布的路由仍会列出——从已存策略中并入、加以标记、可被移除——而不会从仍然固定它的角色中消失。

工作区覆盖编辑器列出每个角色的每个可覆盖字段，在每一项旁显示「继承」或「已覆盖」，并为每一行提供独立的重置，同时为角色和整个工作区提供整体重置。重置会清理被清空的条目，因此字段会回到完全继承的状态，而不是留下一个什么都不记录的补丁。

自动路由区块以保持语义不变的方式迁移了 Plugins 卡片的控件：一个启用开关、一份从全局目录中取出精确提供方/模型路由的复选框清单，以及同一条规则——针对目录已丢弃的模型所保存的路由仍然可见且可移除。该区块写入角色目录自身的 `automaticRouting` 字段。Plugins 卡片保持不动；在退役阶段之前，两者写入的是不同命名空间。

## 备选方案

**把一个受控的模型+推理强度选择器提升到 `ui-primitives`，并让输入区座位重构到它之上。** 这是架构简报给出的第二个选项，能留下一个控件而不是两个。它落选的原因是：输入区的选择器会提交给实时会话，而设置页的选择器发出的是取值，因此这次重构会在一次设置页改动中重写输入区的提交语义；而真正需要共享的部分——目录数据——本就已通过 Host 共享。

**把该页面作为又一张 `settings.plugin.item` 卡片发布。** 它可以复用 Plugins 分区已有的标签页外壳与按命名空间分发的机制。它在形态上落选：卡片只是标签页中的一列，而本页面是一个角色目录，包含按角色编辑器、按角色的工作区覆盖编辑器以及自己的可折叠路由区块。它还会把某个功能的页面放进另一个功能的分区里，而这正是 `settings.section` 槽位存在的意义。

**扩展委派页面而不是新增页面。** 导航条目更少，也不需要新包。它落选是因为两个文档没有任何共同字段：通道是 Command Code 自己的概念、带 CLI 专属的访问词汇，而角色目录的角色与后端无关。合并它们会让一个页面写入两个命名空间，并为同一个控件呈现两套词汇。

**只从 `resolvedRoster` 读取工作区覆盖层。** 这是 Host 自己的答案，也是它所承载取值的正确来源。它作为*唯一*来源落选，是因为已解析的角色视图省略了 `instructions`、`tools` 与 `maxDepth`，因此覆盖每个可覆盖字段的编辑器对其中的三项没有已解析答案。于是编辑器按 Host 所用的同一条规则，从已存定义与工作区补丁推导有效取值，并把已解析读取用于来源信息与卡片摘要。

**像 Plugins 卡片那样暂存编辑并在「保存」时写入。** 这是被接受的设置表单模式，适用于命名空间中有用户可预览文档的卡片。它落选是因为本页面编辑的是由相互独立的角色构成的目录，而不是单个表单：暂存草稿必须跟踪 N 个角色中哪一个被改动过；而最相近的邻居——也正是本页面将替换的委派页面——已经采用针对编辑器当下显示文档的实时组合。

**为模型控件分别提供模式与路由两个控件。** 一个模式下拉加一个路由下拉，是对 `SubagentModelPolicy` 最字面的呈现，也正是 schema 的样子。它落选是因为它让用户回答一个答案本身已经蕴含的问题：「固定且无路由」*就是*继承，「自动」*就是*由 Agent 选择；因此用一个控件在继承 / 由 Agent 选择 / 各模型之间选择，就能表述整个策略，并让推理强度控件的可用性成为单一选择的后果。

## 后果

Harnessy 获得一个页面与一个语言命名空间，角色文档无需重启即可编辑：工具读取的是实时分区，因此已保存的修改会对已在运行的会话的下一次委派生效。

页面只写入字段，不强制执行任何东西。访问级别收窄、调用方式与路由授权都由角色目录插件解析并强制执行，因此此处的缺陷可能误导用户，却无法放宽子进程。页面确实会在原处呈现完全访问的代价，并且从不会把访问级别呈现为 Agent 可以放宽的东西，因为设置界面所用的措辞本身就是保证的一部分，即使机制在别处。

有四项代价是刻意为之的。复制角色会生成一个新的 id 且副本处于禁用状态，因为副本带有相同的用途，同一个任务绝不能在用户审视之前出现第二条生效的路由。工作区无法从本页面移除角色：覆盖层的 `removed` 列表会被读取并清理，但此处没有对应控件。覆盖编辑器的模型行写入整个模型策略，因此工作区要么同时固定路由与推理强度，要么两者都继承。而 Plugins 中的子代理卡片会在旧 `subagent-model-selection` 命名空间退役之前，继续在它之上保留自己的自动路由控件，因此目前有两个控件在授权两个文档上的路由。

选择器是模型控件的第二份实现，这是不触碰输入区的代价。它的边界是清楚的：它只是共享目录之上的呈现层，因此部署新增的提供方或模型会无需本包改动而出现。
