# Agent Note: Harnessy 挂载统一角色目录，并把已存的通道配置带入其中

Status: implemented

[English](2026-09-16-subagent-roster-legacy-migration.md) | 中文

## 问题

统一角色目录作为一个包发布，却没有被任何配置档挂载：它的两个工具触及不到任何 agent，而 Harnessy 用户的角色仍然存放在 `commandcode-delegation` 通道文档中。只挂载该行会让既有用户只拿到角色目录自带的内置角色，而失去他们配置过的角色；按他们命名过的角色进行委派也会因为他们配置本身无关的原因失败。

把旧配置带过来有一条硬约束：通道文档是当时真正在运行的角色唯一记录，而在两个界面并存期间，委派页面仍在写它。任何重写、截断或清空该分区——或其中按工作区的 `projects` 覆盖层——的迁移，都会毁掉它正在读取的来源。

## 决策

`packages/bundle/custom-harness/cordis.patch.yml` 在已有的 `commandcode-delegation` 宿主行旁挂载 `subagent-roster` 宿主行，bundle 清单也声明该依赖。因此两套工具并存：`commandcode_delegate` 与 `list_commandcode_lanes` 继续通过通道分区工作，而 `delegate` 与 `list_subagents` 服务角色目录。退役通道界面是之后的独立变更；本次没有改动旧行、其客户端页面或其文档中的任何内容。

角色目录包中的 `src/migration.ts` 拥有这次一次性迁移，直接接在 `apply()` 中的设置注册之后，因此它运行时所写的分区已经注册就绪。

## 迁移读取什么，以及它何时运行

迁移通过 `settings.describe()` 读取两个旧命名空间，这是唯一能把命名空间的已存用户分区与其解析值分开的公开读取，而两者都需要。已存分区是触发条件：用户从未写入任何内容的命名空间不是待带走的配置，无论其 schema 解析出什么。解析值是来源：只存过 `maxConcurrentRuns` 的用户当时仍有六个通道在运行，因此投影必须复现其配置实际产生的效果，而不是他们键入的那一小段。

当通道命名空间已注册，且用户在任一旧命名空间中存过内容时，迁移运行。无人注册的命名空间、provider 无法读取其已存分区的命名空间，以及只存了空分区的命名空间，都属于同一种普通结果——无事可迁移——因为部署只在自己提供该功能时才挂载旧插件。当模型选择命名空间缺席时，自动路由授权回退到自带默认值，因此只挂载通道插件的部署仍能带走其通道。

守卫最先运行，并读取角色目录自身的已存分区。任何已存的 `subagent-roster` 文档都会终止迁移，包括用户清空了角色列表的文档：那是用户自己的角色目录，迁移的职责是播种文档，而不是替换文档。

## 它写什么，以及拒绝写什么

投影出的文档在写入前由 `validateSubagentSettings` 校验，写入是对 `subagent-roster` 分区的一次 `replace`。两个旧分区都不会被触碰——不论是通道列表、其中的 `projects` 覆盖层，还是模型选择授权——因此旧值仍可查看，也可以通过编辑新文档回退。

每种结果都是宿主日志中的一行：带走了多少角色、无事可迁移、以校验信息拒绝写入，或 provider 拒绝写入。它们都不会抛出，因此任何已存旧值都不可能让加载失败，也不可能连累设置分区。同一次加载中的第二次运行会看到第一次写入的文档，因而什么都不写。

被迁移的角色保留 `execution.backend: 'commandcode'`，因为其通道运行在那里。本阶段没有任何 provider 以该名称注册，因此对这些角色的委派会通过既有的 provider 查找失败，报 `no subagent provider registered for "commandcode"`，并且不启动任何东西；角色目录不会替换成其他后端。

## 本地声明的命名空间名

`src/migration.ts` 在本地声明 `commandcode-delegation` 与 `subagent-model-selection`，而不是从各自所属的包导入。角色目录可与任何配置档组合，而导入任一常量都会让一个与产品无关的包依赖某个产品的后端包。`subagent-commandcode` 中的组合测试会挂载两个真实行、以其归属方自身的常量写入通道分区，并在任一名称漂移时失败——这同时也证明了迁移确实抵达了真实文档。

## 考虑过的替代方案

**导入 `COMMAND_CODE_DELEGATION_NAMESPACE` 与 `SUBAGENT_MODEL_SELECTION_SETTINGS_NAMESPACE`，去掉本地常量。** 这样只有一处事实来源而非三处，且重命名在编译期即可发现。它输在依赖方向上：`subagent-commandcode` 是单一产品的后端，而角色目录是任何配置档都能挂载的通用角色目录。组合测试以同样的保护换来了无需该依赖边。

**只要通道命名空间已注册就迁移。** 这是对“投影既有配置”最简的解读，也不需要比较已存分区。它输在：已注册的命名空间总会解析出自带默认值，因此全新的 Harnessy 安装会用它尚不能运行的六个 Command Code 角色替换掉正在工作的进程内角色。已存分区是区分“配置过”与“用的是默认值”的唯一依据。

**同时要求模型选择那一半。** 把两个命名空间成对读取比回退更整洁。它输在：通道插件与模型选择插件由不同配置档挂载，只挂载通道而不挂载模型选择包的部署将带不走任何东西，而通道才是关键的那一半。

**成功写入后删除旧分区。** 这样只留一个文档而非两个，下一次加载也不再需要守卫。它输在：本阶段委派页面仍在写通道分区，删除会移除一个运行中的界面所拥有的文档；也输在：可回退正是用户信任这次迁移的原因。

**迁移前询问用户。** 设置中的提示是让“看似不可逆”的变更可见的显然做法。它输在：这次迁移并非不可逆——它写入一个新文档并保留全部旧值——也输在插件加载时没有已组合的提示通道，该替代方案等于为一个用户编辑文档即可撤销的决定凭空造出加载时交互界面。

**只投影通道，另行携带选择授权。** 让两个命名空间的迁移相互独立，可以让其中一个先落地。它输在：角色目录的文档是一个分区、一次写入；两次写入需要为它们共同触及的分区再加一道守卫，而“该用户的文档是否已被写入”已由已存角色目录本身回答。

## 后果

Harnessy 会在挂载该行后的首次加载中带走既有用户的角色，只带一次；委派页面与子代理页面并存并继续工作。

对于存过通道配置的用户，被迁移的角色就是他们所配置的 Command Code 角色，因此对它们的委派在注册 `commandcode` provider 之前会响亮失败。这是保留而不是丢弃角色的代价，也正是要断言该失败的原因：`packages/subagent/subagent-roster/tests/migration.spec.ts` 会委派给一个被迁移的角色，并要求得到 provider 查找错误，且没有任何启动请求抵达任何后端。

迁移在每次设置挂载时读取一次 `describe()`，它会解析每个已注册命名空间的 schema。这是加载时开销，只付一次，换来的是唯一能区分用户配置与 schema 默认值的读取。

没有角色的投影会按投影结果写入。已存通道为空的用户最终得到空角色列表而不是自带角色，因为迁移复现其配置而不是替其做主；守卫随后保证后续每次加载都不再触碰它，用户也可以在页面上重新添加角色。
