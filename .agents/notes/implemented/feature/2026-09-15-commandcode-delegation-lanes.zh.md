# Agent Note: Harnessy delegates to Command Code through user-owned lanes

Status: implemented

[English](2026-09-15-commandcode-delegation-lanes.md) | 中文

## 问题

同时使用 Command Code 的 Harnessy 用户希望在会话内把自包含的任务交给该 CLI。有两点使既有的委派面不太合适。

随产品发布的提供方（`dsh-subagent-codex`、`dsh-subagent-claude-code`）注册到 `ctx.subagents`，其全部运行策略都来自组合行。它们的随产品消费者（`dsh-tool-subagent`）随后要么完全不暴露策略，要么在启用 `modelSelectionSettings: true` 时向模型暴露 `provider`、`model` 与 `reasoning_effort`。这两种形态都无法承载按调用的 **通道** —— 即模型、推理强度与访问级别的具名组合 —— 而不把访问级别本身交给模型，而这恰恰是被委派任务绝不能扩大的字段。通用 subagent 接缝也没有通道字段，而增加一个字段会让单一产品的概念支配所有官方组合共享的契约。

Command Code 还拥有自己的安装、认证、模型目录与权限标志。Harnessy 不得内置或再分发 `command-code` npm 包（其许可为 UNLICENSED），不得读取或保存其凭据，并且在它不可用时不得静默回退到任何其他产品、模型或可执行文件。

## 决策

`@deepseek-ai/dsh-subagent-commandcode` 是既有接缝之上的专用消费者，而不是注册到 `ctx.subagents` 的提供方。它在调用时从实时设置命名空间解析当前工作区的通道，并直接驱动用户自己的 CLI，同时复用 subagent 接缝的进程外词汇（`settleRun`、`settleRunResult`、`subprocessRunHandle`、`SubagentResult`、`SubagentRun`）以及通用作业注册表进行后台调度。

该消费者拥有三件事：

- **`commandcode-delegation` 设置命名空间**：保存全局通道目录、三项运行上限（`maxConcurrentRuns`、`timeoutMs`、`maxTurns`），以及按规范工作区路径为键的 `projects`（按工作区通道覆盖）。覆盖是字段补丁：未提及的字段继承，提及的字段替换。删除通道会一并删除所有针对它的覆盖。
- **两个 token 稳定的模型可见工具。** `list_commandcode_lanes` 报告为该工作区解析出的已启用通道 —— id、name、purpose、model、effort、access —— 别无其他。`commandcode_delegate` 接受通道 id、自包含任务与可选的 `run_in_background`；它没有模型、强度、超时、轮数、可执行文件、凭据或权限字段。
- **`commandcode` Remote 命名空间**：只暴露 CLI 检测到的版本与登录状态、其仅供参考的模型目录，以及某个工作区解析出的通道。任何机密、路径或进程事实都不经它传输。

有两点让模型可见契约保持诚实。任务书写入 CLI 的 stdin（`-p` 不带查询参数是其文档化的管道输入形式），因此任务文本不会进入 argv，也不会有任何 shell 看到这些取值。而父会话可见文本在本包的运行处就限定为 12 KiB UTF-8，因此每个消费者都继承同一上限与同一截断标记。

后台委派先注册，再做其他一切。作业注册表同步返回 id，随后它调用的启动函数在一个任务自有的控制器下拥有 CLI 预检、并发名额、进程与拆除 —— 因此调用方绝不会被更早的运行或探测阻塞。杀死仍在探测或排队的作业会以 killed 结算：不启动任何 Command Code 进程，并归还它已持有的名额，或根本不曾占用名额；从未进入运行的委派会以失败作业结算，其 detail 与失败运行使用同一套固定的产品自有诊断，绝不会是主机路径、命令或原始产品错误。

`custom-harness` bundle 补丁层挂载两部分。由于 Host 行把两个工具注册到根作用域，任何 Harnessy 预设组合出的 agent 都能看到它们 —— 这正是官方 web bundle 会禁用 host 面工具行的原因 —— 而其他配置档根本不挂载该行。

## 曾考虑的替代方案

**在 `ctx.subagents` 上注册 `commandcode` 提供方。** 这是同类形态，能复用最多机制。它因通道而落选：接缝的 `SubagentStartRequest` 没有通道字段，而唯一可能承载它的请求字段（`agentOptions`、`persona`）含义不同，并被按不同含义校验。增加通道字段会把单一产品的策略放进所有官方组合共享的契约中。

**通过 `tool-subagent` 的 `modelSelectionSettings` 暴露通道的模型与强度。** 这样无需新增包。它落选是因为该路径把模型选择 **暴露给模型**，而访问级别在其中根本没有字段 —— 因此访问级别只能来自组合行，而那不是按工作区的，也不是运行时可编辑的。

**为每个通道注册各自的 `ctx.subagents` 提供方实例。** 这很有吸引力，因为生命周期事件与闭包语义可以免费获得。它落选是因为通道属于实时设置：新增、重命名或删除通道都必须在每次设置变更时协调一个全局提供方注册表，而在协调期间开始的运行会与其提供方身份竞争。在调用时读取通道则没有这个窗口。

**把任务书放入 argv。** CLI 文档化了 `cmd -p "query"`。它因两点落选：契约要求在 CLI 支持时把任务文本排除在 argv 之外，而 CLI 确实支持 —— 其无头参考文档记录了 `echo "…" | cmd -p` —— 并且 Windows 的命令行上限远低于真实任务书的大小。

**由随产品发布的 Agent 预设行挂载工具。** 这符合其他所有工具抵达 Harnessy agent 的方式。它落选是因为预设文件由所有配置档共享：一行命名只有 Harnessy bundle 会安装的包，在官方配置档中将无法解析。在产品补丁层挂载插件能够触达同样的 agent，因为工具注册表的全局层对每个作用域可见，同时不影响官方配置档。

**在 `SubagentStartRequest` 中增加通道字段。** 出于上述原因被否决：单一产品的策略不属于共享接缝，否则每个官方提供方都必须决定如何处理它。

**让通用作业注册表以「最终输出作业」的方式交付最终答案。** 去掉 `readOutput` 会让 `JobRegistry.read()` 返回结算结果中的 `output`，这显然是取得后台答案的途径。它落选是因为契约同时要求在运行期间给出粗粒度的当前类别，而流式作业的 `read()` 根本不会查询该结算结果。因此该钩子同时承担两半：运行期间给出活动增量，结算之后给出与前台调用完全一致的有界文本。

**把共享的安装探测绑定到首个调用方的信号上。** 通过记忆化 promise 去重探测，正是让页面加载不会为每个读取方各起一对辅助进程的原因，但限制它的信号属于最先发问的那一方 —— 于是该读取方取消时，会把一个健康的 CLI 变成对所有其他人不可用，而后来者的取消又会被忽略直到首个探测结束。现在探测运行在插件自己持有的控制器之下，每个调用方各自让自己的取消与它竞速，而已经取消的调用方根本不会启动探测。

## 后果

Harnessy 获得了一个委派后端，且没有新增接缝、没有新增进程所有者，也没有改动 `agent-loop` 或 `dsh-subagent`。代价是一个专用消费者，其通道解析与作业适配由它自己拥有，并且每次委派会产生两个短生命周期辅助进程用于探测（同一时刻只保留一个，从而去重）。被委派的运行无法通过 `subagent/start` 与 `subagent/end` 观察；其活动状态改为通过通用作业运行时的完成通知与 `job_output` 到达父会话。

这条决策的内核是：访问级别是存储的策略，绝不是调用参数。任何会让任务扩大它的东西 —— 按调用覆盖、由模型选择通道、回退到其他可执行文件 —— 都在契约之外，而两个工具 schema 由 Loader 组合测试逐字固定，因此之后的任何改动都必须是有意为之。

设置页面为这条策略付出的代价是它自有的写入路径。每次编辑都作用于编辑器当前显示的分区，并且只写入它真正改动的顶层字段，因为写入要晚一个往返周期才会抵达镜像快照，否则同一次往返内的两次编辑都会各自从同一份过期文档重新推导。每次被接受的写入之后都会重新读取已解析视图 —— 当有更新的读取取代它或页面卸载时中止该次读取 —— 因此继承状态与重置控件会收敛到 Host 已提交的内容，而不是页面最后一次看到的内容。
