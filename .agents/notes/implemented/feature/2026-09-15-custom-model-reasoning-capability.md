# Agent Note: Custom models declare their own reasoning capability

Status: implemented

English | [中文](2026-09-15-custom-model-reasoning-capability.zh.md)

## Problem

A model a deployment declares by hand — an OpenAI-compatible gateway such as Command Code with `deepseek/deepseek-v4.1-flash` listed under `llm-pi-ai` — streamed requests fine but never showed the composer's reasoning-effort control, even on an endpoint that accepts `reasoning_effort`.

The capability abstraction itself already existed and already reached every consumer. `LlmAdapter.resolveModel()` returns `LlmResolvedModelInfo.reasoning` (ordered efforts plus an optional default), `LlmRuntime` validates it and refuses an unsupported request effort with `UNSUPPORTED_REASONING_EFFORT`, `buildModelCatalog` projects it onto the browser wire, the composer picker renders exactly those levels, and `preflightChildLlmRoute` resolves every child route through the same call. Built-in adapters populate it from their own catalogs. `llm-pi-ai` could already declare it per model through `PiAiModelProfile.reasoningEfforts`, whose keys are the offered levels and whose values are their wire spellings.

Two gaps kept that from being a product capability. Nothing in the Models page wrote the field, so a custom route could only be given levels by hand-editing `settings.yaml`. And the profile's only default effort was route-level (`PiAiProviderProfile.reasoning`), so two models under one route could not dispatch different defaults even though their offered level sets already differed.

## Decision

The existing abstraction is extended; nothing gained a second reasoning vocabulary. `LlmResolvedModelInfo.reasoning` remains the one source of truth read by the composer picker, the Session model catalog, ACP, and the subagent preflight, and the provider adapter remains the only place a normalized effort becomes a request field.

`PiAiModelProfile.defaultReasoningEffort` names the level a model's requests dispatch when they name none. It wins over the route-level `reasoning`, which stays the fallback for every model that declares none of its own. `RouteCatalog.configuredReasoningDefaults` carries it by model id, the same split `configuredMaxTokens` already uses: the offered levels are the model's capability and live on the materialized pi-ai `Model` as `thinkingLevelMap`, while the request default is the deployment's choice and never enters that model. Resolution refuses a default that is not one of the entry's own `reasoningEfforts` keys, and refuses any default beside omitted or `false` efforts, because neither state names a level that could supply the wire spelling.

The Models page's model row owns the capability editor, inside the disclosure that already held the capacities. It declares one of three states — the adapter's own answer (the field is omitted), an explicit support with its offered levels, or an explicit refusal (`false`) — then the offered levels and the default one. The level vocabulary is read out of the adapter's own `Config` schema (`reasoningEffortChoices` in `ui-settings-models`, the same mechanism `protocolChoices` already uses for wire protocols), so the page offers exactly the levels the adapter accepts rather than a list this client maintains. Each row declares independently, which is what makes two models under one route disagree without either affecting the other.

The editor writes the normalized level name as the wire spelling — `low: 'low'`, and `off: null` for the level whose wire form is the parameter's absence. A gateway that spells a level differently still sets its own `reasoningEfforts` value in `settings.yaml`; the row's controls name the offer, and the profile's value remains the translation.

An existing custom model keeps working untouched: an omitted `reasoningEfforts` still means "no declaration here", the row shows the adapter's default answer, and editing any other field of that row never materializes a claim nobody made. That is also why the declaration is a three-way control rather than a checkbox: for a shipped route whose entry inherits catalog reasoning, "not declared" and "declared not to reason" are different requests, and a two-state control would have to call one of them something false.

## Where a model's levels come from

Resolution order is fixed, and each step states only what it actually knows. The provider's own metadata comes first: a `GET /models` entry that carries `reasoningEfforts` — camel or snake case, with an optional `defaultReasoningEffort` that must name one of them — has those levels read by `dsh-llm-pi-ai`'s discovery and carried to the surface, so adopting that model starts from the provider's answer instead of asking the user to restate it. The installed catalog comes next: for a route pi-ai ships, discovery reports the level set `getSupportedThinkingLevels` records for that exact model, and resolution already inherits it when the profile entry declares nothing. An explicit per-model declaration comes third, and anything left over is undeclared, which shows no effort control at all.

Nothing is completed from anything else. A listing that states no levels yields none; a level list that is empty, non-array, offers only `off`, or contains unusable members yields only the usable ones or nothing; a default outside its own list is dropped rather than repaired. `LlmRuntime.discoverModels` is the one normalization every reply passes through, so those rules hold no matter which adapter answered. Provenance is not stored on the row: where a level set came from is a property of the read, not of the model, so the picker labels the source of the list it is showing rather than persisting a claim that would rot as the provider changes.

The Model Editor's fetch picker therefore shows each candidate's exact levels, named the way the composer will name them, above a line naming whether that list came from the adapter's installed catalog or from the provider's own listing; the route's `declared` flag is what tells the two apart, because a route the adapter ships is answered without ever reaching the network. Adopting a candidate writes those levels into the row through one conversion shared with the row's own checkboxes, so an imported set and a hand-picked set store identically, `off` included — whose wire form is the parameter's absence. A row that declares nothing says so where the control is, and says which of the two routes to a set applies to it. A row that declares nothing else is the one case adoption fills in: an imported level set replaces an absence, while every value the row does state, a refusal and a tuned capacity included, still wins.

## Capabilities a provider publishes outside its model listing

Some providers answer model capability questions through a channel the model-listing endpoint does not touch. Command Code is the worked example: its `--list-models` listing carries an id and a description, and its `--effort low|medium|high` flag is a fixed vocabulary that says nothing about which level a given model takes — `deepseek/deepseek-v4-pro` takes `high` and `max`, `z-ai/glm-5.3-flash` takes `low`, `high`, and `max`, and `Qwen/Qwen3.8-Flash` takes `low`, `medium`, and `xhigh`. Assuming the flag's three values for every model would be wrong for all three.

`LlmRuntime.registerModelCapabilitySource` is the one extension point for that case. An installed integration registers a lookup that answers by exact model id — and receives the discovery request, because bare model ids are not unique across providers — and the seam consults it only for a model whose adapter stated nothing, so a provider's own listing always wins. The answer passes through the same normalization as an adapter's statement: usable members survive beside unusable ones, a set offering only `off` is not a capability, and a default that names no stated level names nothing. Discovery is where this lands, not resolution: a per-model answer keyed by id would otherwise be attributed to any route serving that id, and a name like `claude-sonnet-5` is not Command Code's alone.

`@deepseek-ai/dsh-subagent-commandcode` is the first source. It reads the catalog the CLI ships and validates its own `model:effort` shorthand against — `bundled/command-code-knowledge/reference/models.md` beside the installed entry point, whose `Efforts` column states each model's levels and dashes the models that decide their own depth — resolving it lazily on the first lookup. It answers only for routes that name Command Code or point at a `commandcode.ai` endpoint, and it preserves Command Code's level names exactly rather than translating them, because the seam's normalization and the adapter's own key vocabulary are the translation layers.

## Alternatives considered

**A provider-scoped reasoning control.** Rejected: the models under one provider disagree about their levels, so a provider-level switch could only name a set some of them reject, which would take the whole route out of every picker.

**Introducing the `ModelCapabilities` type as specified.** Rejected: an equivalent abstraction already ships as `LlmResolvedModelInfo.reasoning`, is already validated by `LlmRuntime`, and is already read by every consumer. A second type would have created the duplicate capability metadata the global design forbids.

**A boolean "Reasoning" checkbox.** Rejected: the declaration has three states, and a checkbox would have to render a catalog model that reasons as "off" — a control that states the opposite of what the request does.

**A client-side list of effort levels.** Rejected: it would drift from the adapter's `THINKING_LEVELS` silently. Reading the union off the owning namespace's schema cannot drift, and the display copy for a level this build has no name for falls back to the level id.

**Auto-claiming reasoning for every custom model.** Rejected: an endpoint's `/models` listing reports ids and capacities, never a reasoning protocol, so the claim would be a guess that breaks existing models. Manual declaration stays available, and the profile can still be written by hand.

**A route-level reasoning default.** Rejected: the models under one route disagree about their levels, and Command Code's own catalog shows how far that goes — `deepseek/deepseek-v4-pro` offers `high` and `max`, while `Qwen/Qwen3.8-Flash` offers `low`, `medium`, and `xhigh`. One declaration per route would claim a set most of its models reject.

**Answering a capability source at resolution rather than discovery.** Rejected: a source is keyed by model id, and ids such as `claude-sonnet-5` are not unique to the provider whose registry states them, so resolution-time enrichment would attach one provider's levels to another provider's model with nothing for the user to review. At discovery the levels are shown before anything is stored.

## Consequences

A hand-declared model reached through the product can declare reasoning, its levels, and its default, and every consumer picked them up without a change. The profile format gained a field, so the generated config catalog, the providers guide, and both package READMEs were updated with it.

The cost is that the model row's disclosure now carries capabilities beside capacities, so its label reads "Capabilities"; and that a gateway whose wire spelling differs from the level name is still configured in `settings.yaml`, because the row deliberately offers the normalized levels rather than a per-level value editor.

`packages/test-support/llm-replay` declares its own per-model `reasoningEfforts`/`defaultReasoningEffort` vocabulary for the replay adapter. Its `string[]` shape is the one this work adopted for the discovery wire type, but the adapter's own configuration was not unified with this one.

The Command Code delegation path states nothing either way: the only metadata its integration reads is the CLI's `--list-models` text listing, parsed into `{ id, description }`, and its effort is a per-lane run flag. Its shipped catalog is where the per-model sets above come from, and a CLI update that changes the catalog changes what the source answers without any change here.
